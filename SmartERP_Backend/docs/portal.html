Authentication Architecture

JWT Tokens & HTTP-Only Cookie Lifecycle

SmartERP uses a secure, dual-token JSON Web Token (JWT) architecture designed for browser-based ERP workflows:

1. Login & Token Generation

Clients send credentials to POST /api/v1/users/login. On successful bcrypt password verification, the server generates:

  • Access Token: Short-lived JWT (default 1 day) signed with ACCESS_TOKEN_SECRET containing { user_id, email, name }.
  • Refresh Token: Long-lived JWT (default 10 days) signed with REFRESH_TOKEN_SECRET containing { user_id } and stored in the users table.
  • Cookie Delivery: Tokens are sent as HttpOnly; Secure; SameSite=Strict cookies (accessToken and refreshToken) preventing client-side script access (XSS mitigation), while also returned in the JSON response payload.
2. Verification & Session Guard

Protected endpoints pass through the auth middleware:

  • Extracts token from req.cookies?.accessToken with fallback to Authorization: Bearer <token> header.
  • Verifies token validity; attaches the authenticated user record to req.user.
  • Returns 401 Unauthorized ("Please Login") if the cookie/header is missing, forged, or expired.
  • Logout (POST /api/v1/users/logout): Clears the database-stored refresh token and invalidates client cookies.
Token Refresh Note: The controller function refreshAccessToken is implemented in src/controllers/user.controller.js, but is currently not mapped to an active route in user.routes.js. Clients should prompt re-login when the access token expires.

Multi-Tenancy & Role-Based Access Control

Company Isolation & Permissions Matrix

SmartERP enforces multi-tenant data segregation. Every company's business data (items, suppliers, customers, categories, units, vouchers) is isolated using the :company_id path parameter and governed by the company_access middleware. Users are mapped to companies via company_users(user_id, company_id, role).

Authentication vs. Authorization Status Codes:
• HTTP 401 Unauthorized: Missing, expired, or invalid credentials (accessToken). The client must authenticate.
• HTTP 403 Forbidden: Valid session authenticated, but the user either does not belong to the target company_id (rejected by company_access) or lacks the required role (rejected by checkRole(['owner', 'manager'])).

Core Business Logic

Inventory Stock Mechanics & Voucher Settlement Bounds

All voucher operations in SmartERP run within atomic PostgreSQL transactions (BEGIN / COMMIT / ROLLBACK) to maintain strict inventory and accounting integrity:

Real-Time Inventory Stock Flow
  • Purchase Vouchers (POST /api/v1/purchase-voucher/{company_id}): Inward stock. Verifies supplier belongs to company, generates purchase voucher items, and automatically increments items.current_quantity = current_quantity + quantity for each received line item.
  • Sales Vouchers (POST /api/v1/sale-voucher/{company_id}): Outward stock. Verifies customer belongs to company and performs an atomic pre-sale stock sufficiency check (current_quantity >= quantity). If any item has insufficient stock, the transaction aborts with HTTP 400 Insufficient stock. When sufficient, it decrements items.current_quantity and records line items.
Voucher Settlement & Financial Bounds
  • Payment Vouchers (POST /api/v1/payment-voucher/{company_id}): Outward payments to suppliers against purchase vouchers. Computes cumulative prior payments (SUM(amount)) and strictly prevents overpayment: total_paid + new_amount <= total_purchase_amount. Excess payment throws HTTP 400.
  • Receipt Vouchers (POST /api/v1/receipt-voucher/{company_id}): Inward customer payment collections against sales vouchers. Computes cumulative receipts and enforces total_received + new_receipt <= sales_voucher_amount. Excess receipt throws HTTP 400.

Data Standards & Validation

API Response Envelopes & Zod Validation

All SmartERP endpoints adhere to standard response wrappers defined in ApiResponse and ApiError utilities:

Standard Success Envelope (HTTP 200 / 201)
JSON Success Format
{
  "statusCode": 200,
  "data": {
    "item_id": 1,
    "item_name": "Premium Basmati Rice",
    "current_quantity": 150
  },
  "message": "Item fetched successfully",
  "success": true
}
Standard Error Envelope (HTTP 400 / 401 / 403 / 404 / 409 / 500)
JSON Error Format
{
  "statusCode": 400,
  "message": "Validation failed",
  "success": false,
  "errors": [
    {
      "field": "body.contact_no",
      "message": "Contact number must be a valid 10-digit Indian phone number"
    }
  ]
}
Zod Request Validation: Endpoints validate incoming req.body, req.params, and req.query using Zod schemas before reaching the controller. Path parameters (company_id, item_id, etc.) are coerced to positive integers. Validation failures return HTTP 400 with granular field-level diagnostics.
